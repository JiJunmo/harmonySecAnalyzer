# 分支覆盖与跨轮连续性改造方案

状态：已按本方案实现运行协议 25。接口以 progressive-semantic-exploration.md 和 Schema 为准；真实项目的模型覆盖质量仍需验证。

## 1. 目标和范围

探索阶段需要回答四个问题：当前检查了哪段代码、哪些分支还没检查、为什么停止、换一个 Agent 后如何继续。

保持整体流程：项目初始化与组件识别 -> 组件渐进语义分析 -> 组件连接 -> 六维验证 -> 报告。每个组件仍只有一个持久语义任务，可分轮运行；run.db 仍是唯一可变状态源。

本次重做探索内部的覆盖记录、待办表达、上下文恢复和完成判定。不引入新的分析 Agent，不重新实现 Atlas，不建立第二个数据库，不建立逐语句符号执行引擎。

### 已确认的设计缺陷

| 当前问题 | 根因 | 本方案处理 |
|---|---|---|
| 函数内多个分支难以分别保存进度 | 节点身份以函数为中心，resume 只有一个位置 | 用源码范围表示工作，分支入口和汇合位置进入覆盖图 |
| 相同函数的不同调用可能合并或被拒绝 | 去重和关系校验主要按目标函数名 | 调用位置、进入条件和已检查范围参与区分 |
| 换轮后不知道之前分析过什么 | 已存步骤被压缩为一句摘要 | 提供结构化覆盖记录、相关结果及可查询的完整历史 |
| 共享节点恢复错误前序 | 只有首次 parent_node_id 被用于回溯 | 本次工作显式关联入边和来源，不能由首次父节点决定上下文 |
| 停止深入某个调用后漏掉后续代码 | 停止作用范围及调用返回位置不明确 | 分开记录内部展开边界、当前分支退出和调用后续 |
| 已登记任务做完即认为组件完成 | 缺少独立的代码范围覆盖记录 | 完成检查覆盖范围、分支去向及所有已知待办 |
| 协议复杂但只保证填写自洽 | 同一关系在多个数组反复声明 | 统一提交覆盖变化、关系和事实，由脚本推导调度与汇总 |

## 2. 主流程

1. 领取当前工作：组件、代码范围、进入条件、已有结果、剩余分支和必要前序。
2. 核实当前范围的控制流结构：先看当前函数或局部代码段有哪些出口，再深入其中的分支。
3. 分析连续代码：查询 Atlas，必要时直接核实源码，记录安全事实和调用关系。
4. 保存本次增量：已检查范围、新发现的分支、调用及其后续、停止依据、剩余工作。
5. 脚本落盘并检查覆盖记录：有待办则继续；达到本轮容量则换上下文；全部范围闭合后生成语义结果。

发现敏感操作后继续分析后续代码。分支是否需要登记不以“已经判断它有安全意义”为前提。

## 3. 覆盖图和工作项分开

### 3.1 覆盖图表示源码结构

节点表示组件分析范围内一个可定位的代码范围或位置，包括函数入口、连续代码段、分支入口、汇合位置、调用位置和出口。函数名是归属信息，不再是唯一工作身份。

节点至少保存：所属组件、所属函数、源码起止位置、节点类型。位置使用相对路径、行列；同一位置的不同结构角色通过节点类型区分。节点 ID 由脚本生成，Agent 使用本次提交的局部引用或运行时已返回的 ID。

边表示真实去向：条件分支、顺序继续、调用、调用后继续、异常转移以及已确认的复用。分支条件属于边；源码位置和事实说明共同支撑关系。

例如：

```text
handle 入口 -> if 条件
                +-- true  -> 调用 helper(read) --+
                +-- false -> 调用 helper(delete)-+-> 汇合 -> 操作 C -> 返回
```

两个调用位置分别记录，不能因为目标都叫 helper 就合并。helper 内部的结构可以共享，具体分析进度按进入条件区分。

### 3.2 工作项表示某种条件下尚需分析的范围

工作项关联覆盖图中的范围，并保存进入条件、相关输入约束、身份、安全检查、来源入边和必要的调用后续引用。

工作状态仅存在于工作项：待处理、处理中、已处理。已处理表示该范围的处理结果已保存；范围内仍存在子待办时，不代表整个函数覆盖完成。停止和缺口是处理结果的原因，不再增加另一套同义任务状态。

同一步已分析完的分支可以批量登记为已处理，不需要经历领取和派发。只有剩余工作进入队列。一个 Agent 轮次可以连续处理多项工作。

### 3.3 存储安排

复用 exploration_nodes 和 exploration_edges，调整为覆盖结构及真实关系。新增 exploration_work_items，保存具体范围在特定上下文下的分析进度和租约；不新增独立分支状态表。

节点不再同时保存排队、租约和函数完成状态。节点覆盖状态、分支覆盖统计从工作项和处理结果推导。现有结构化事实继续在数据库中保存，提交增量和结构变更使用同一事务。

## 4. 分支怎么登记与分析

### 4.1 先确定局部结构，不先枚举全组件路径

首次进入函数时阅读函数结构，登记直接包含的分支、调用后的公共代码及出口。嵌套分支在进入对应代码范围时再展开。

函数很大时可以按源码范围分段登记，但必须保留未检查区域的明确待办。已读到某个 if 时，其两个出口都应登记；没有 else 时，false 出口指向后续语句。switch 要考虑 default 或未匹配出口；循环要保存退出去向；try/catch/finally 要按源码记录可见处理结构。

不能因为一个分支暂时未发现敏感行为而不登记，也不要求把普通赋值和每个语句分别建节点。没有需要继续跟踪的行为时，可以批量记录已检查范围和处理依据。

### 4.2 分支范围和公共后续

每个分支工作有明确起止范围。分支内完成后，沿已登记出口进入汇合位置；提前 return 的分支不连接普通汇合点。

连续多个 if 通过公共后续连接，不枚举所有完整路径组合。到达汇合位置时，保留仍影响后续行为的输入约束和安全状态；不能把互斥条件拼成同时成立的状态。

### 4.3 调用后的继续分析

普通调用在当前路径中连续分析，证据并入路径结果，不要求逐个建图。仅在显式独立展开或需要跨轮时，同时登记调用目标和调用后续工作及其依赖。

目标返回值、异常或状态修改影响调用者时，先取得对应事实，再继续分析受影响的后续。异步注册和同步调用分别处理，不能强制等待不会同步返回结果的回调。

多个调用者可以共享被调用代码的结构；每个调用者的返回位置独立保留。循环和递归只处理新增的相关状态，无法确定状态变化边界时保留缺口，不能仅凭“见过此函数”认定已覆盖。

## 5. 跨轮恢复什么信息

explore-next 返回脚本整理的工作上下文，不再使用首次父节点链上的摘要代替分析现场。

| 默认提供的信息 | 内容 |
|---|---|
| 当前范围 | 函数、位置、范围边界、当前应检查的分支或语句 |
| 进入条件 | 本次真实入边、有效条件、相关输入取值约束、身份和安全检查 |
| 当前范围覆盖 | 已检查子范围、待办分支、停止分支及原因、公共后续 |
| 调用后续 | 调用者返回位置、异常去向、仍需查明的返回值或状态影响 |
| 已有事实 | 历史默认提供操作组索引、安全检查及停止依据；当前范围与返回依赖保留完整结果，其他详细证据按需查询 |
| 已检查调用 | 普通内联调用的证据保存在路径结果，不要求单独建图；已显式登记的调用保留位置和条件 |
| 处理去向 | 已登记的继续、停止、复用关系，以及目标工作当前进度 |

必要信息直接提供。历史原文、完整证据和其他分支详细结果，通过同一个 audit_orchestrator.py 的只读查询入口按范围或步骤读取；命令和定位参数由运行时返回，Agent 不直接操作数据库。

上下文过大时分页提供，并明确还有哪些记录未载入。不能静默截断条件、停止依据或待办列表。Agent 只领取当前明确范围；仅当历史证据影响当前判断或复用时查询详情，不为范围闭合重读全部历史，脚本自行核对已登记结构的闭合。

自然语言 summary 只用于阅读，不参与调度、去重、覆盖判定或状态恢复。

## 6. 停止判断的可信度

停止不是单一开关，必须说明作用范围和源码依据。

| 处理结果 | 要求 | 对其他工作的影响 |
|---|---|---|
| 当前分支退出 | return/throw 位置及适用条件，交代可见的异常处理和 finally | 只关闭当前执行范围；保留调用者和其他出口 |
| 不深入目标内部 | 已确认的组件、平台或第三方边界，调用位置、目标依据和可见效果 | 保留调用后续；组件通信仍输出组件调用事实 |
| 后续不再受攻击者影响 | 说明输入、身份和调用触发如何均不再影响后续行为，提供源码依据 | 只能关闭证明覆盖到的范围，不得把某个参数变为常量当作整体终止 |
| 复用已分析结果 | 已完成范围引用及相同的适用条件 | 连接已有结果，保留本次来源和返回位置 |
| 无法确定 | 已尝试核实的内容、位置和未解决问题 | 记录覆盖缺口，其他可分析出口继续 |
| 本轮容量不足 | 未完成范围和恢复状态 | 保存待办，下一轮继续，不能转为正常停止 |

运行时检查引用、范围和去向是否完整、是否误关其他工作；Agent 负责源码语义判断。每次提交前在当前上下文中复核本次关闭的范围，检查调用后续、其他分支和异常出口，不新增独立停止复核任务。

不要求所有关系都有两处源码证据：函数内条件边由对应控制流位置证明；动态调用补全仍需要调用点和绑定/分派依据。结构关系不能被迫伪装成 Atlas 调用关系。

Atlas 未命中时先核实相关源码；完整解析后继续，部分解析则继续已确认目标并保留剩余缺口，完全不能解析才只保留缺口。

## 7. 归并与规模控制

1. 结构按源码位置共享，分析按相关条件区分。read/delete 等影响执行的取值不能只压缩为 preserved。
2. 不使用整条历史路径作为去重键。进入条件只包含仍影响当前范围行为的约束，历史来源作为证据引用保留。
3. 首版只自动复用相同范围、规范化后完全一致的相关条件与状态。语义等价但文本不同的条件不自动认定等价，不新增条件求解器。
4. 已不影响后续的条件可以在源码依据支持下退出当前状态；这一判断仍属于 Agent 的语义责任，脚本不假装能够证明条件失效。
5. 图节点数量不等于任务数量；同轮连续处理，按批次保存增量，不要求每个分支一次工具调用。
6. 本轮容量用于保存和换上下文；组件总预算作为用户可见的异常保护。旧的 64 节点、8 轮硬限制不能直接沿用到更细的覆盖图。
7. 预算耗尽时列出未完成范围，禁止伪装为已覆盖。规模保护可能影响完整性，应在报告中明确显示；不承诺同时实现无限规模和完整覆盖。

## 8. 提交协议如何简化

步骤围绕三类内容提交：覆盖结构与处理进度的变化、带位置的调用关系、语义事实。暂停请求仍只表达是否换上下文。

删除或替换：

- 单独的 resume 对象：当前函数、其他函数、其他分支的剩余工作统一使用范围工作项。
- 单独的 analyzed_symbols 清单：已分析调用和范围从覆盖记录推导。
- Atlas 目标清单与 resolved_relations、successors 之间重复的函数名集合对账：仅保留必要的显式关系及证据，普通调用并入路径事实；工具原始观察可以作为证据保留。
- 首次 parent_node_id 回溯生成 path_context：改为本次工作关联的来源、条件和结构化记录。
- 由 Agent 同时声明多个同义状态：工作状态由脚本维护，覆盖结论由记录推导。
- 节点保存成功直接代表范围完成：记录事务成功、工作已处理和整个范围闭合分别解释清楚。

校验集中在真正影响连续性的约束：引用存在、来源匹配、已知分支有去向、未完成范围有待办、关闭范围有依据、复用条件匹配、事实可定位。对不同文字表述不增加任意枚举或关键词校验。

## 9. 完成判定与下游边界

组件完成需要：入口候选有处理结果；已登记函数范围没有未查看区域；已登记分支都有处理结果或明确缺口；调用后续全部处理；没有排队、处理中或等待结果的工作。

存在缺口时生成部分覆盖结果，并保留未完成范围。没有任务排队但仍有未满足的调用后续依赖，属于流程阻断，不能判为完成。

最终语义结果继续由脚本生成，操作组保留分支条件和证据来源。函数只有在对应范围和适用条件都闭合后才能列为完成检查，不能由“曾出现过这个符号”推导。

六维验证和组件连接继续使用现有语义结果接口；必要的分支定位作为证据关联传递，不让下游参与探索调度。报告同步展示已登记分支、处理结果、缺口、停止理由和调用后续。

这里的完整性仅指已登记范围的覆盖。模型可能遗漏最初的源码结构；函数结构核实和结束前范围复核用于降低风险，不能宣称具备编译器级控制流完整性证明。

## 10. 实现安排

| 阶段 | 工作内容 | 验收门槛 |
|---|---|---|
| 一：统一范围模型 | 修改数据库、步骤契约和归一化写入；替换函数名身份、单个 resume 和多数组对账 | 同函数不同分支、同目标不同调用位置能分别记录；重复提交幂等 |
| 二：闭环探索 | 接入领取、连续分析、范围待办、结构化恢复、调用后续及停止检查 | 跨轮不丢待办和条件，调用后续可恢复，未闭合范围不能完成 |
| 三：端到端收口 | 同步 Agent/Skill、语义汇总、报告、增量兼容检查、部署 smoke；清理旧字段与规则 | 三种审计范围及增量运行共用新协议，部署包完整，规模没有按分支数放大任务数 |

三个阶段是开发顺序，不发布新旧协议混用的中间版本。开发可用固定数据和针对性测试验证，完整闭环通过后再用于真实项目。

主要修改文件：store.py、semantic_exploration.py、semantic_results.py、task_context.py、scheduler.py、cli.py、步骤 Schema、component-semantic-analyzer.md、两个工作流 Skill、reporting.py 及相关增量/部署测试。

新增代码文件仅在职责确实需要时引入：优先将上下文读取与整理集中到一个 exploration_context.py，避免继续扩大状态机文件。只读查询使用现有脚本入口，不新增独立可执行脚本。具体文件拆分在实现前结合函数依赖确定。

旧运行数据库不尝试把一句摘要还原成完整分支状态。新协议需更新版本标识：旧探索任务不能直接续跑；旧报告可以保留。增量基线中旧协议的语义结果不能被静默视为满足新覆盖标准，需重新分析对应组件并更新基线。这是一次性兼容边界，不维护两套长期探索协议。

## 11. 重点验收用例

| 用例 | 必须得到的结果 |
|---|---|
| 同函数 if/else 分别存在操作 A/B，之后还有公共操作 C | 三处操作均被发现，两个分支可定位，公共后续不遗漏 |
| 一个分支 return，另一分支继续敏感操作 | return 只关闭所属分支 |
| 两个位置以不同参数调用同一个 helper | 可分别分析、跨轮保存，不因相同函数名被拒绝或错误复用 |
| 进入 helper 后暂停，调用者后面还有敏感操作 | 新轮恢复 helper 及调用后的继续位置 |
| 本轮完成一个分支、停止一个分支，另有两个分支未完 | 下一轮能看到四者的事实与去向，已完成范围不重复分析 |
| 不同分支进入共享函数，身份或取值条件不同 | 不使用首次父节点的上下文替代本次来源 |
| 系统 API 后还有安全检查和敏感操作 | 停止深入系统内部，但继续检查调用者 |
| try/catch/finally 包含敏感行为 | 相应出口和 finally 工作不因 throw 被清除 |
| 多个连续 if 汇合，后续不依赖分支差异 | 共用后续结构，条件退出有依据，不枚举全部历史路径 |
| Atlas 缺失动态边，源码确认部分候选 | 已确认目标继续，剩余缺口保留，其他分支不受阻断 |
| 分支多但函数短 | 批量登记和分析，不为每条分支创建子 Agent |
| 达到轮次容量或组件总预算 | 前者续跑，后者输出明确未完成范围，不误报完整覆盖 |

自动化测试验证协议和状态连续性。真实项目抽查验证模型是否正确登记源码分支、停止依据是否成立；两类验证不能相互替代。
